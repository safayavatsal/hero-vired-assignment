# AI Usage

## Deliberately authored work

The project is being developed as peer programming. The project owner directs and approves the design; implementation logic is AI-assisted and reviewed against that design.

- High-level architecture, low-level classes, relationships, API catalog, data model, and service boundaries.
- Baseline runtime decisions, local Compose workflow, credential handling, port allocation, and safety boundaries.
- Feature acceptance criteria, scenario expectations, runbook structure, and final review direction.

## AI-assisted implementation

- Runtime wiring, simulator scenarios, alert normalization, correlation, deduplication, persistence, investigations, model boundary, paging, actions, durable jobs, recovery, timeline APIs, frontend console, evaluation cases, and demo scripts.
- Tests, migrations, Docker wiring, local HTTP boundary adapters, evidence masking, structured response validation, retry behavior, and UI selection safeguards.

## Verification findings and human direction

The project owner identified, prioritized, or reviewed the following grouped findings during verification:

- **Build and runtime:** missing frontend type declarations, incomplete test-image contents, worker startup ordering, environment propagation, network egress, and container test permissions.
- **Workflow correctness:** duplicate delivery, correlation, stale decisions, timeline ordering, investigation state, durable jobs, paging fallback, action approval, idempotency, execution attempts, and verification recovery.
- **Model and evidence safety:** provider configuration, request format, bounded evidence, masking, citations, structured output, degraded status handling, persistence, and retry behavior.
- **UI behavior:** stable incident selection, scenario/target matching, stale response protection, active page/action selection, investigation controls, evidence review, queued states, replies, and timeline context.
- **UI interaction review:** the owner identified stale responder targeting, cluttered step labels, generic inline failures, and repeated action clicks. The UI now uses the newest page record, exposes server validation details in a dismissible toast, blocks duplicate work while queued, and gives each workflow section one clear primary action.
- **UI comprehension review:** the owner identified raw JSON overload and unclear live-demo sequencing. The UI now leads with a guided workflow, a plain-language investigation result, labeled evidence fields, readable timeline summaries, collapsed evidence/audit sections, and opt-in raw payload disclosure.
- **UI review follow-up:** the owner identified cluttered controls, missing reply availability after acknowledgement, premature action buttons during queued investigations, and scenario-selection mismatch. The frontend now groups workflow controls, derives the scenario from the selected service, keeps replies available through acknowledgement, and blocks actions until investigation completion.
- **Workflow status clarity:** the owner identified that the progress strip could mark a step complete merely because a record existed. The frontend now distinguishes ready, locked, active, and verified states so the operator always knows the next valid action.
- **Simulator flow gap caught during audit:** the owner’s clean-demo review exposed that generated simulator alerts were only stored in simulator state and did not create incidents. The simulator now emits webhook-ready payloads through the canonical alert intake path; flapping deliveries also use distinct lifecycle event identities and source ordering.
- **UI feedback issue caught during verification:** the owner identified that a repeated investigation could look frozen while the result refresh was pending, and that the three workflow areas were difficult to understand. The frontend now confirms accepted actions in a toast, releases the button without waiting for the worker refresh, and labels the workflow by user intent.
- **End-to-end demo issue caught during verification:** the owner identified that investigation, response, and action controls were visible together and that the final verification could fail after a worker completed the action. The workflow is now sequential, shows background progress, and verifies from the persisted worker result across the API/worker process boundary.
- **Assignment-flow closure issues caught during verification:** the owner identified that a completed investigation did not produce a clear terminal timeline state, verified remediation did not close the incident, reply follow-up could become inert, and an external-dependency finding could look like it needed a local action. The implementation now records investigation completion, `resolved`, and `unfixable` outcomes, keeps follow-up response controls active, and labels no-local-fix cases explicitly.
- **Delivery quality:** HLD/LLD/API alignment, golden evaluations, runbooks, repeatable demos, local Docker/PostgreSQL proof, frontend build proof, and explicit separation between verified behavior and future add-ons.
- **Frontend structure:** the owner-directed UI cleanup keeps screen orchestration, domain types, reusable selection helpers, and styles in separate folders without adding a component framework or unnecessary abstraction.
- **Realistic-investigation review:** the owner identified that generic fixture evidence and hidden model output made the result difficult to trust. The implementation now uses concrete e-commerce signals, names each bounded evidence query, persists safe telemetry, and renders the structured model readout beside the deterministic finding.
- **Final browser review:** the owner identified that repeated responder content obscured the workflow. The refreshed UI has one responder section, sequential controls, labeled evidence cards, collapsed raw details, and a visible toast when a background investigation is accepted.
- **Demo realism gap:** the owner identified that API fixtures alone did not demonstrate a customer failure reaching an on-call engineer. The AI-assisted implementation adds a deliberately synthetic store, a privacy-bounded payment-failure alert, and a local captured-email responder path; the owner retains the product and demonstration decisions.
- **Observed-application integration:** the owner directed removal of customer-facing operator shortcuts and adoption of an embedded observer boundary. The AI-assisted implementation keeps event delivery separate from the customer payment outcome and sends no payment credentials in its operational event.
- **Repeatable demo verification:** the owner’s smoke-run review identified that separate checkout attempts could join the same incident through broad service-time correlation. The AI-assisted implementation now preserves explicit correlation-key boundaries so each new checkout attempt can demonstrate its own incident and responder path.
- **Live-session readiness review:** the owner directed a parity pass against the assignment’s on-site demands using researched reference systems. The review found that adding a scenario required code changes in three places. The AI-assisted implementation moves finding rules into scenario data, registers scenarios at runtime through the documented endpoint, and derives the console’s scenario metadata from the public listing, so a described incident can be added and investigated without code changes.
- **Live-scenario loading issue caught during final verification:** the owner identified that a newly registered scenario could arrive after incident details and leave the console on the default scenario. The frontend now reselects the scenario matching the selected incident service, with a focused regression test and a TypeScript declaration for the shared helper.
- **Submission-safety issue caught during final review:** the owner required reviewer-ready decisions and defensible model output. The implementation now rejects malformed structured responses before persistence, and the repository includes a concise scale/safety summary mapped to the on-site workflow.
- **Submission-proof gap caught during final review:** the owner required a repeatable final check rather than separate commands. The AI-assisted implementation adds a local preflight that checks the Compose boundary, both backend suites, frontend builds, commerce workflow, and diff integrity; the owner retains the submission decision.
- **Deployment wiring issue caught during browser verification:** the store HTML loaded while its backend proxy returned `502`. The AI-assisted implementation now makes the proxied health route a Docker/Kubernetes readiness gate and a required submission-preflight check; the owner retains the deployment decision.
- **Customer-demo coverage issue caught during assignment review:** the store could demonstrate only a payment-provider failure from the browser. The AI-assisted implementation now adds customer-facing slow-checkout and delayed-fulfillment journeys, maps them to the existing incident scenarios, and extends the repeatable commerce proof; the owner retains the scenario and demonstration decisions.
- **Investigation explainability issue caught during final review:** the backend already persisted evidence queries and model telemetry, but the browser hid most of that provenance behind raw JSON. The AI-assisted implementation now presents a plain-language investigation brief, provider status, response time, tool trace, query timing, and progressive evidence details; the owner retains the review and presentation decisions.
- **Workflow language issue caught during review:** the owner identified that the scenario selector looked like a manual diagnosis and that owner acknowledgement and remediation approval were unclear. The AI-assisted implementation now presents the matching scenario as investigation context, keeps controlled overrides advanced-only, and explains notification, approval, queueing, execution, and verification as separate human-visible steps; the owner retains the product and presentation decisions.
- **Sequential workflow issue caught during review:** the owner identified that normal rerun, responder follow-up, and remediation approval were presented as overlapping actions. The AI-assisted implementation now separates the completed finding from an explicit deeper investigation, closes ownership after acknowledgement, explains the recommended action from evidence, and sends captured notifications to a specific resolved or configured owner; the owner retains the workflow and communication decisions.
- **Remediation review issue caught during browser verification:** the owner identified that “Review action” created an approval record without showing what would change. The AI-assisted implementation now provides a read-only sandbox projection with before/after state and projected changes; only the explicit Approve or Reject choice creates the audited action decision.
- **Investigation explainability enhancement:** the owner wanted the investigation path to be understandable before a live demo starts. The AI-assisted implementation adds scenario-owned bounded checklists that visibly move from pending to active to complete while the existing worker-backed investigation runs; the owner retains the scenario and presentation decisions.
- **Evidence-boundary enhancement:** the owner wanted the investigation to explain not only the result, but also what each bounded query is for. The AI-assisted implementation adds a read-only tool catalog and persists each tool's purpose and enabled state beside its trace; the owner retains the review and presentation decisions.
- **Resource-analysis enhancement:** the owner approved broader resource diagnosis without changing the assignment workflow. The AI-assisted implementation adds a separate read-only analyzer contract, six resource analyzers, explicit filters, normalized findings, and focused tests; the owner retains the capability and safety decisions.
- **Visible resource-analysis gap caught during verification:** the owner identified that the analyzer API was not visible in the existing console. The AI-assisted implementation now adds a runnable sample scan, problem/resource counts, finding cards, and a read-only notice to the browser workflow; the owner retains the presentation and safety decisions.
- **Resource-health discoverability issue caught during verification:** the owner identified that the panel was too easy to miss below the incident list. The AI-assisted implementation now places it in a dedicated top-level `Kubernetes health` tab while keeping the incident workflow as the default view; the owner retains the navigation decision.
- **Local deployment extension:** the owner requested Helm packaging as an extension to the existing assignment. The AI-assisted implementation adds a local chart for the existing runtime, including probes, resource bounds, persistence, security contexts, port-forward notes, and a smoke-test hook; the owner retains the deployment and submission decision.
- **Historical-context enhancement:** the owner required similar past incidents without changing deterministic diagnosis. The AI-assisted implementation adds pure-Python vectors, PostgreSQL persistence, bounded ranked retrieval, graceful degradation, and a separate console panel; the owner retains the retrieval and review decisions.

These contributions are recorded as human detection, direction, and verification; implementation changes remain explicitly attributed as AI-assisted.

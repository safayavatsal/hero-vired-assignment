# Plan Incident UI

## Goal

Provide the required incident list and complete incident timeline.

## Steps

1. Add an incident list with status, severity, service, summary, owner, and last activity.
2. Add an incident detail page with current state and investigation summary.
3. Render timeline event types for alerts, correlation, evidence, findings, pages, replies, decisions, actions, verification, failures, and resolution.
4. Show evidence references and raw details without allowing raw text to become executable UI controls.
5. Show available human actions based on backend-provided permissions and current state.
6. Refresh or stream updates without duplicating events.
7. Show loading, empty, unavailable, and error states.

## Acceptance checks

- A user can find an incident and understand its complete history.
- A user can acknowledge, reply, approve, or reject from the incident page.
- UI state reflects backend truth after refresh.
- Failed and unknown operations are visibly distinct from success.

## Implementation status

Implemented:

- Incident list with service, summary, severity, status, and alert count.
- Incident list includes last update time, and the timeline renders display-safe event payloads.
- Incident detail with ordered timeline events.
- Five-second refresh and empty/error states.
- Inline page acknowledgement and typed action proposal, approval, rejection, execution, and verification controls.
- Selected incident identity is preserved across five-second list refreshes.
- Stale detail responses cannot overwrite a newer incident selection.
- Page controls prefer a delivered page, and action controls use the latest proposal.
- Frontend selection behavior has a built-in Node smoke-test command.
- Investigation control loads the persisted investigation for the selected scenario.
- Evidence review shows findings, confidence, uncertainty, citations, source availability, timestamps, and masked payloads.
- Action controls require a matching completed investigation and ignore stale proposals for another scenario or service.
- Selected incidents refresh in place so queued worker results become visible without changing the user's selection.
- Responders can submit free-form replies, and queued/running action states are shown separately from completed or unknown outcomes.

Verified locally on 2026-10-22: the frontend container served HTTP 200 on port 8000, and its backend workflow controls were exercised against the live API on port 8001.

Boundary verification:

- External notification and ownership remain opt-in backend boundaries and are not required for the local UI workflow.
- Live model verification is confirmed through the worker-backed path with the configured provider credential; the UI handles completed, unavailable, and degraded results.
